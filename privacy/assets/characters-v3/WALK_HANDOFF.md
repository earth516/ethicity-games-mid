# 걷기 시트 제작·연결 인계

2026-10-18. 실제 작업 트리의 `js/map.js`, `js/sprite-dom.js`, `js/palette.js`, `css/style.css`를 읽어 확인했다. 이 작업은 이 문서만 작성하며 게임 코드·기존 PNG를 변경하거나 commit/push하지 않는다. 사용자 목적은 **7명 걷기 그림 제작**이며 이 문서는 제작 완료 보고가 아니다.

## 확인 상태

- 검사 시점에 이 폴더의 `walk-*.png`는 없었다. 아래 1024×1536은 예상 납품 규격이지 검증된 이미지 크기가 아니다. 생성·디코딩·16칸 내용·알파·실제 애니메이션 검증은 메인 제작 작업자가 수행해야 한다.
- 기존 `assets/sprites/char_*.png` 9개의 PNG 헤더는 모두 192×288, `minjun_sleep.png`는 48×72였다. 헤더 확인은 이미지 육안 검증을 대신하지 않는다.
- 이미 있는 `*-map-front.png`는 단일 정면 참고 그림이다. 걷기 시트로 대체 연결하지 않는다.
- 기존 미커밋 변경(map.js, 테스트 파일, 신규 에셋 폴더)이 있었다. 이를 이번 문서 작업의 변경이나 검증 결과로 간주하지 않는다. 게임 실행·브라우저 합성 검증은 이번 작업에서 하지 않았다.

## 실제 로더 계약과 주의점

### Canvas 맵

- `map.js:94–107`의 `loadSprite(key,file)`는 `assets/sprites/`에 파일명을 붙이고, onload에서 모든 캐릭터를 `PrivacyPalette.image(im,true)`로 보정한다. 실패하면 `false`로 저장해 도형 fallback을 사용한다. 캐시 키가 이미 있으면 재시도하지 않는다. 남녀 선택 변경 때는 `sprites.me`를 지운다.
- `show()`와 `stage()` 양쪽이 NPC에는 `char_<who>.png`, 주인공에는 `char_player_<m|f>.png`를 요청한다. 이 두 경로를 함께 지원해야 한다. `minjun_sleep`는 별도 파일·별도 그리기 계약이다.
- `ROW`는 **down=0, left=1, right=2, up=3**. `drawPerson()`(587행 이후)은 원본 폭/4와 높이/4로 자르므로 192×288 및 1024×1536 모두 소스 크롭 계산 자체는 가능하다. 원본 칸은 각각 48×72와 256×384이다.
- **경로만 교체하면 안 된다.** onload가 `srcTile=im.naturalWidth/4`로 바꾼다(100–104행). `resize()`와 `draw()`는 이 값을 표시 타일 크기로 사용한다: `T=srcTile*max(1,round(viewW/(srcTile*13)))`. 새 원본을 그대로 넣으면 일반 맵의 T는 최소 256이 되고 캐릭터는 256×384 이상으로 커진다. 구·신규 시트를 섞으면 마지막 로드된 일반 시트 폭에 따라 전체 맵 배율이 바뀔 수도 있다.
- 실제 목적지 크기는 **T×1.5T**이지 항상 48×72가 아니다. 기존 기준 T=48일 때 48×72, 배율에 따라 96×144 등이며, 방 안 걷기는 별도의 T=28~96 맞춤 계산을 사용한다. 원본 해상도와 표시 기준 48을 분리해야 기존 화면 구도를 보존한다.
- 목적지 좌상단은 `(sx,sy-0.5T)`, 발 기준은 `(sx+0.5T,sy+T)`. 각 프레임을 독립 bbox로 확대·센터링하면 발이 흔들린다. 일정한 셀·몸 크기·발 기준선을 유지하고 충돌 판정은 기존 월드 타일에 둔다.
- `walkFrame()`(424행)은 이동 중 `floor((walked+t)*2)%4`, 정지 시 0이다. STEP_MS=150이므로 연속 이동은 약 75ms/프레임, 네 프레임 순환은 약 300ms다. `me.frame` 증가값은 실제 그리기 프레임 선택에 쓰이지 않는다. NPC는 항상 프레임 0을 그린다(547행). NPC의 걷기 그림을 납품해도 현재 게임에서 NPC가 자동으로 걷지는 않는다.
- `resize()`는 `imageSmoothingEnabled=false`를 설정한다. 고해상도 비픽셀 그림 축소 품질은 실제 크기에서 별도 확인한다. 필요하면 새 캐릭터 drawImage에만 smoothing을 켜고 즉시 이전 값을 복구한다. 전체 타일 렌더링 설정을 일괄 변경하지 않는다.

### DOM 얼굴/전신

- `sprite-dom.js:9–12,21,38–40`: 파일 경로는 기존 `assets/sprites/char_*.png`; CSS 논리 시트는 192×288, 전신 48×72, 얼굴 크롭은 `(2,0,44,38)`이며 항상 **맨 위 행 첫 칸**을 쓴다. 기본 scale=2이다.
- `background-size:192*k px 288*k px`로 원본 전체를 강제 축소하므로 **같은 4×4 격자의 1024×1536도 URL만 바꾸면 기하학적으로 호환**된다. SHEET/FULL/FACE를 원본 해상도로 바꾸지 않는다. 얼굴의 위치·비율이 기존과 다르면 얼굴 크롭의 미적 적합성은 보장되지 않는다. 큰 투명 상단 여백이나 큰 머리 때문에 잘리는지 확인한다.
- DOM은 palette를 호출하지 않는다. `.spr`에는 `image-rendering:pixelated`가 있다(`style.css:382`). 비픽셀 신규 그림은 별도 클래스 등으로 `auto`를 적용하는 것이 후속 선택이다. 걷기 그림 제작만을 위해 DOM을 바꿀 필요는 없다.

### 색 보정

- `palette.js`는 같은 크기의 canvas로 RGB를 보정하고 알파는 유지한다. canvas에 `naturalWidth/Height`도 붙여 맵의 기존 크롭 계산을 지원한다. 캐릭터는 명도 최대 가산 계수 0.045, 채도 배율 1.16(피부 색상 범위는 1.02), 채도 상한 0.94이다. 픽셀 읽기 실패 시 원본을 반환하므로 file://와 HTTP에서 결과가 달라질 수 있다.
- 이미 완성된 새 밝은 그림에는 **신규 시트만 원본 Image를 저장해 보정을 우회**한다. 기존 char_friend·잠든 민준·환경 이미지의 보정은 유지한다. 맵 전체 시간대 tint는 별개로 이후 적용된다. DOM은 원래 보정하지 않으므로 신규 우회는 양쪽 색 차이도 줄인다.

아래 신규 경로는 모두 `assets/characters-v3/` 기준이며, 아직 존재/검증을 의미하지 않는다.

## 권장 최소 연결 방법 — 후속 작업용, 미적용

1. 우선 7개 원본을 현재 폴더에 제작·검증한다. 기존 192×288 PNG를 덮어쓰거나 이 문서를 이미지 납품으로 대체하지 않는다.
2. 검증 후 맵 로더 안에 위 **기존 요청 파일명→신규 URL** 매핑을 둔다. 매핑된 파일은 `im.src`에 신규 URL, 나머지는 기존 `SPRITE_DIR+file`을 사용하면 show/stage 호출부를 모두 고칠 필요가 없다.
3. 표시 기준 `srcTile=48`을 유지하고 onload의 원본 폭 기반 srcTile 변경 블록을 제거한다. drawPerson의 `naturalWidth/4`, `naturalHeight/4`는 그대로 둔다. 이것이 고해상도 원본과 기존 192×288 시트를 동시에 사용하는 핵심 수정이다. 현재 설치본은 모두 48px 셀이므로 기존 배율을 보존한다(옛 32px 시트의 자동 배율 선택은 더 이상 계약으로 삼지 않음).
4. 매핑된 신규 시트만 `sprites[key]=im`, 나머지는 기존 palette 호출을 유지한다. 그림 로드/크기 실패 시 기존 파일로 재요청하는 fallback을 추가하려면 신규 URL 시도 여부를 구분하고, 이미 null로 채워진 캐시를 둔 채 loadSprite를 재호출하지 않는다. fallback은 권장 보강이며 현재 구현은 도형 fallback뿐이다.
5. **걷기만 연결하는 최소 범위에서는 DOM 로더를 유지**한다. 이후 얼굴도 통일할 때 같은 파일 매핑을 DOM에 적용하되 CSS 논리 크기는 유지하고 얼굴 크롭·pixelated 스타일만 실제 이미지로 검토한다. 신규 캐릭터에 한정한 smoothing은 실제 축소 비교 후 결정한다.

대안: 최종 192×288 런타임 파생본을 별도로 제작하면 기존 타일 크기 추론은 문제되지 않는다. 다만 고해상도 원본을 보존하고 48×72에서 다시 품질 확인해야 하며 URL 연결·중복 색 보정 문제는 여전히 남는다. 단순 파일 덮어쓰기는 권장하지 않는다.

## 제작·검증 통과 조건 (미완료)

- PNG 실제 디코딩 후 가로·세로가 4로 나누어지는지와 2:3 비율 확인. 1024×1536이면 정확히 256×384씩 16칸이다. 생성기가 정확한 격자를 보장한다고 가정하지 않는다.
- 행은 아래/왼/오/위, 열 0은 중립 정지. 권장 열 순서는 중립→한쪽 발→중립 복귀→반대쪽 발로, 실제 0→1→2→3→0 반복 시 보행이 자연스러워야 한다. 네 장의 동일 포즈 복제는 걷기 완성이 아니다.
- 7×16=112칸 모두 알파·유효 인물·셀 경계 침범·잘린 머리/발/가방·발 기준선·크기 흔들림을 확인한다. 체크무늬가 그려진 불투명 배경과 실제 투명 알파를 구별한다. 전역 모서리 투명 여부만으로 통과시키지 않는다.
- 남녀 주인공의 파란 후드/노란 가방, 하윤 갈색 단발/안경, 서아 금발, 도현 붉은 머리, 민준 푸른 머리, 담임 성인 복장 등 정면 참고 그림의 정체성이 모든 방향에서 유지되는지 육안 확인한다. 좌우는 화면 기준 방향이며 뒷모습을 정면 복제로 처리하지 않는다.
- 실제 48×72/96×144 축소와 4방향 애니메이션을 확인한다. 동일 발 앵커, 셀 사이 그림 섞임, 확대/축소 및 팔·다리 변형을 검토한다. DOM 교체 시 얼굴 크롭도 따로 확인한다.
- 후속 연결 검증은 남/여 전환, NPC 정지, 잠든 민준, 기존 friend, 실외와 방 안 배율, 시간대 tint, HTTP/file://, 누락 이미지 fallback을 포함한다. 격리 미리보기 검증과 실제 게임 합성 검증을 구분해 보고한다.

**현재 결론: 로더 조사와 연결 권고만 완료. 신규 걷기 PNG 제작·검증·게임 연결 성공은 아직 확인하지 않았다.**
